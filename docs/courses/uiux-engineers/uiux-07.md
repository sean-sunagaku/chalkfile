# 第 7 章　アクセシビリティ: 誰でも使える画面

- 講座: エンジニアのための UI・UX デザイン（uiux-engineers）
- 章 ID: `uiux-07`　動画 ID: `D07`
- 動画: 08:26（62 台詞）
- 要約: 見え方や使い方が違う人も、同じように使える画面にする。WCAG 2.2 の 4 つの原則と、代替テキスト・キーボード・フォーカス・ターゲットのサイズの達成基準を、サンプル予約の日時を選ぶ画面と、div のボタンと button 要素のコードで確かめる。JIS X 8341-3 と ISO の関係、改正障害者差別解消法の合理的配慮と環境の整備も押さえる。

## 学習目標

- WCAG 2.2 の 4 つの原則とレベル（A・AA・AAA）を説明し、目安とするレベルを決められる
- 代替テキスト・キーボード・フォーカス・ターゲットのサイズの達成基準を、自分の画面で点検できる
- ボタンを div ではなく button 要素で作る理由を、キーボードと読み上げの動きで説明できる
- JIS X 8341-3・WCAG・ISO の関係と、改正障害者差別解消法の合理的配慮と環境の整備の違いを説明できる

- HTML のボタンと画像（img の alt）を書いたことがある

### [uiux-07-s01] 困りごと: 同じ画面でも、使えない人がいる

根拠: 説明用の仮の例・公式・法令・規格　動画の場面: 3　出典: [デジタル庁 2025-10-16 更新](https://www.digital.go.jp/resources/introduction-to-web-accessibility-guidebook)

サンプル予約の「日時を選ぶ」画面に、次のような声が届いたとします（**架空の例**です）。

- **画面を読み上げて使う人**: 日付の横の矢印が、何のボタンか分からない
- **キーボードだけで使う人**: 「予約へ進む」に、Tab キーで届かない
- **画面を拡大し、キーボードで進む人**: 選んだ所が、画面の下に固定した帯に隠れて見えない
- **指先が震える人・片手で使う人**: 小さな日付を押し間違える

どれも、マウスでふつうに操作する作り手には気づきにくい問題です。見た目が整っていても、使えない人がいます。デジタル庁のガイドブックは、視覚に障害がある人だけでなく、けがで一時的に手が使えない人のような、さまざまな状況の利用者を挙げ、年をとるにつれて見る・聞くなどの力が下がることは誰にでも起こる、とも書いています。

### [uiux-07-s02] WCAG の 4 つの原則とレベル

根拠: 公式・法令・規格　動画の場面: 4　出典: [W3C 2023（2024-12-12 更新）](https://www.w3.org/TR/WCAG22/)、[情報通信アクセス協議会 ウェブアクセシビリティ基盤委員会（WAIC） 2024-12-12 版の訳（作業中）](https://waic.jp/translations/WCAG22/)、[W3C Web Accessibility Initiative（WAI） 2025-10-21](https://www.w3.org/WAI/news/2025-10-21/wcag22-iso)、[ウェブアクセシビリティ基盤委員会（WAIC） 2026（お知らせの一覧では 2026-09-28）](https://waic.jp/news/news-7938/)、[デジタル庁 2025-10-16 更新](https://www.digital.go.jp/resources/introduction-to-web-accessibility-guidebook)

WCAG（Web Content Accessibility Guidelines）は、W3C が作るウェブのアクセシビリティの指針です。今の版は 2.2（2023 年 10 月に勧告、2024 年 12 月に更新）で、2025 年には国際規格 ISO/IEC 40500:2025 にもなりました（W3C のお知らせ）。

WCAG 2.2 は、4 つの原則の下に 13 のガイドラインを置き、その下に、確かめられる達成基準を並べています（訳語は WAIC の参考訳）。

- **知覚可能**: 情報と画面の部品を、利用者が受け取れる形で示す（画像の代替テキスト、文字のコントラストなど）
- **操作可能**: 画面の部品と移動を、操作できるようにする（キーボード、フォーカス、ターゲットの大きさなど）
- **理解可能**: 内容と操作の仕方が分かる（ラベル、エラーの特定など。第 6 章のフォームの基準の多くはここ）
- **堅牢**: 支援技術を含む、いろいろな利用者の道具で、正しく解釈できる（部品の名前・役割・値をプログラムが読めるなど）

達成基準には A・AA・AAA の 3 つのレベルがあり、A が最低限です。WAIC の解説は、AA を国内外の公的機関などで求められる水準とし、AAA は目的に応じて取り入れるもので、すべてを満たすことは勧められていない、と説明しています。デジタル庁のガイドブックも、政府のシステムの調達では JIS X 8341-3:2016 の AA 準拠を目標にするのが標準的だとしています。

### [uiux-07-s03] この章で確かめる 5 つの達成基準

根拠: 公式・法令・規格　動画の場面: 5　出典: [W3C 2023（2024-12-12 更新）](https://www.w3.org/TR/WCAG22/)、[情報通信アクセス協議会 ウェブアクセシビリティ基盤委員会（WAIC） 2024-12-12 版の訳（作業中）](https://waic.jp/translations/WCAG22/)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

- **1.1.1 非テキストコンテンツ（A）**: 画像などには、同じ役割を果たすテキストの代替を付けます。ボタンやリンクになっている画像は、見た目ではなく**働き**を書きます（「矢印」ではなく「次の週」）。飾りの画像は、支援技術が読み飛ばせるように、空の alt（alt=""）にします（W3C の解説）
- **2.1.1 キーボード（A）**: すべての機能を、キーを押すタイミングを求めずに、キーボードで操作できるようにします。手書きの線のように、動きの道筋そのものが要る機能だけが例外です。W3C の解説は、キーボードで操作できれば、音声入力やスクリーンキーボードのように、キーボードの代わりになる道具を使う人にも役立つとしています
- **2.4.7 フォーカスの可視化（AA）**: キーボードで操作できる画面には、フォーカスの枠が見える状態がなければいけません。CSS で outline を消して代わりの見える枠を用意しないのは、W3C の解説が挙げる失敗例（F78）です。:focus-visible を使って枠を出す方法があります（C45）
- **2.4.11 隠されないフォーカス (最低限)（AA、2.2 で追加）**: フォーカスを受けた部品が、作り手の置いた物（固定のヘッダーやフッター、クッキーの帯など）で**全部**隠れないようにします。一部が隠れるだけなら満たしますが、より厳しい 2.4.12（AAA）は一部も隠さないことを求めます。CSS の scroll-padding で、固定の帯の分の余白を取る方法があります（C43）
- **2.5.8 ターゲットのサイズ (最低限)（AA、2.2 で追加）**: ポインタで押す所は 24×24 CSS ピクセル以上にします。例外は、小さくても、ターゲットの中心に合わせて直径 24 CSS ピクセルの円を描き、ほかのターゲットや円と重ならない（間隔）、同じ働きの別の部品が基準を満たす（同等）、文の中のリンク（インライン）、ブラウザが決めた大きさのまま（ユーザエージェントによる制御）、その見せ方が欠かせない（必要不可欠）の 5 つです。W3C の解説は、24 は最低限で、大きいほど多くの人が使いやすいとしています。より厳しい 2.5.5（AAA）は 44×44 CSS ピクセルです

### [uiux-07-s04] 規格と日本の制度

根拠: 公式・法令・規格　動画の場面: 6, 7　出典: [情報通信アクセス協議会 ウェブアクセシビリティ基盤委員会（WAIC） 2016](https://waic.jp/docs/jis2016/understanding/201604/)、[ウェブアクセシビリティ基盤委員会（WAIC） 2026（お知らせの一覧では 2026-09-28）](https://waic.jp/news/news-7938/)、[W3C Web Accessibility Initiative（WAI） 2025-10-21](https://www.w3.org/WAI/news/2025-10-21/wcag22-iso)、[情報通信アクセス協議会 ウェブアクセシビリティ基盤委員会（WAIC） 2024-12-12 版の訳（作業中）](https://waic.jp/translations/WCAG22/)、[内閣府 2024 年 4 月 1 日施行の改正](https://www8.cao.go.jp/shougai/suishin/sabekai.html)、[内閣府（2023 年 3 月 14 日閣議決定） 2023](https://www8.cao.go.jp/shougai/suishin/sabekai/kihonhoushin/r05/pdf/honbun.pdf)、[デジタル庁 2025-10-16 更新](https://www.digital.go.jp/resources/introduction-to-web-accessibility-guidebook)

**規格の関係**: 日本の JIS X 8341-3:2016 は、ISO/IEC 40500:2012（WCAG 2.0）と内容が一致する規格です（WAIC の解説）。そのため、WCAG 2.1 と 2.2 で増えた基準（2.4.11・2.5.8・3.3.7 など）は入っていません。WCAG 2.2 は 2025 年に ISO/IEC 40500:2025 になり（W3C のお知らせ、2025-10-21）、WAIC は、JIS もこれを受けて改正する見込みで、順調なら 2027 年、遅くとも 2028 年としています。

WCAG 2.2 は前の版の基準を引き継いでいて、2.2 に合うサイトは 2.0・2.1 にも合うように作られています。W3C は、決まりが古い版を指していても、新しい目標として 2.2 を採ることを勧めています。デジタル庁のガイドブックも、スマートフォンで使う人が多いことから、JIS に加えて WCAG 2.1・2.2 の基準への対応を検討する必要があるとしています。この講座では、**WCAG 2.2 の AA** を目安にします。

**日本の制度（一般的な説明です。個別の判断は専門家に確かめてください）**: 障害者差別解消法は 2021 年に改正され、2024 年 4 月 1 日から、事業者による**合理的配慮の提供が義務**になりました（第 8 条 2 項。それまでは努力義務）。障害のある人から、社会の中のバリアを取り除いてほしいという意思が示されたとき、負担が重すぎない範囲で、その人に合わせた対応をすることです。

一方、前もって多くの障害者が使えるように整えることは「**環境の整備**」と呼ばれ、行政機関と事業者の**努力義務**です（第 5 条）。国の基本方針（2023 年 3 月閣議決定）は、環境の整備を、不特定多数の障害者を主な対象にした事前の改善の措置とし、その例に情報アクセシビリティの向上を挙げています。デジタル庁のガイドブックも、ウェブアクセシビリティへの取り組みを、合理的配慮を提供するための環境の整備として努力義務が課されたもの、と説明しています。

基本方針は、両者の関係の例として、オンラインの手続きのサイトが使いにくいという申し出に電話やメールで応じ（合理的配慮の提供）、そのあとサイトを改良する（環境の整備）場面を挙げ、2 つを両輪で進めることが大事だとしています。サンプル予約に当てはめると、「使いにくいので電話で予約したい」と言われたら電話で受け、同時に予約の画面そのものを直す、ということです。

### [uiux-07-s05] 良い例・悪い例: 日時を選ぶ画面と、div のボタン

根拠: 説明用の仮の例・公式・法令・規格・実務の指針　動画の場面: 8, 9　出典: [W3C Web Accessibility Initiative（WAI） —](https://www.w3.org/WAI/ARIA/apg/patterns/button/)、[MDN Web Docs（Mozilla） 2026-08-21 更新](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/button_role)、[W3C 2023（2024-12-12 更新）](https://www.w3.org/TR/WCAG22/)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

動画では、日時を選ぶ画面を改善前と改善後で比べました（図 uiux-07-f02）。大事な違いの多くは、見た目には出ません。

- **矢印のボタン**: 改善前は、div の中に画像を置いただけで、画像に alt がない。キーボードでは止まらず、読み上げでは何のボタンか分からない。改善後は button 要素にし、画像の alt に「次の週」と働きを書く。ボタンの名前は、ふつう中の文字（ここでは alt）から決まる
- **日付**: 改善前は小さな数字が詰まって並び、押し間違えやすい。改善後は 24×24 CSS ピクセルよりずっと大きいボタンにし、あいだをあける
- **予約へ進む**: 改善前は、見た目だけボタンの div で、クリックでしか動かない。改善後は button 要素（type="submit"）にする。W3C の WAI-ARIA APG によれば、ボタンは、フォーカスがあるとき Space でも Enter でも押せるもので、button 要素なら、その動きが最初から入っている

div のまま直すこともできますが、MDN は、role="button" は意味を伝えるだけで、押す動きは付かないと書いています。tabindex="0" でフォーカスを受けられるようにし、Enter と Space のキーの処理も自分で書く必要があります。そのうえで MDN は、できる限り button 要素などの元からあるボタンを使うよう勧めています（図 uiux-07-f03）。

フォーカスにも、よくある落とし穴があります。デザインに合わないからと CSS で outline を消すと、キーボードの人は今どこにいるか分からなくなります（2.4.7）。消すなら、代わりのはっきりした枠を :focus-visible などで用意します。画面の下に「予約へ進む」の帯を固定するなら、フォーカスした部品がその帯の下に全部隠れないよう、scroll-padding などで余白を取ります（2.4.11）。

### [uiux-07-s06] 判断と限界: 自動チェック・補助の機能・ARIA・例外

根拠: 公式・法令・規格・実務の指針　動画の場面: 10　出典: [デジタル庁 2025-10-16 更新](https://www.digital.go.jp/resources/introduction-to-web-accessibility-guidebook)、[W3C Web Accessibility Initiative（WAI） 2024-03-21 更新](https://www.w3.org/WAI/test-evaluate/easy-checks/)、[MDN Web Docs（Mozilla） 2026-08-21 更新](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/button_role)、[W3C Web Accessibility Initiative（WAI） —](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)、[W3C Web Accessibility Initiative（WAI） WCAG 2.2 の解説](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)

**自動チェックの限界**: チェックツールは多くのページを短い時間で調べられて便利ですが、デジタル庁のガイドブックは、ツールで確かめられるのは達成基準の 2〜3 割程度だとし、目で見る確認・キーボードだけの操作・スクリーンリーダーなどでの確認を必ず行うよう書いています。たとえば alt があるかは分かっても、その文が働きに合っているかは、人が見ないと分かりません。W3C の Easy Checks も、手早い点検は網羅的ではなく、通っても大きな問題が残ることがある、としています。

**補助の機能を足せば済むわけではない**: デジタル庁のガイドブックは、文字の拡大ボタンや色の切り替えボタンをサイトに付ければアクセシビリティが確保できる、という考えを誤解として挙げています。利用者は、ふだん使う端末の設定で文字の大きさや色を変えていることが多いからです。端末の設定に合わせても崩れない作りにすることと、読み上げで意味が伝わり、操作できるように作ることが先です。

**ARIA より、元からある要素**: ARIA の属性で意味を足すことはできますが、元からある要素で済むなら、それを使います（MDN）。W3C の WAI-ARIA APG は「No ARIA is better than Bad ARIA」と書き、間違った ARIA は、ないより悪いことがあるとしています。role="button" を付けるのは、ボタンに期待されるキーボードの動きを自分で作る、という約束をすることでもあります。

**例外を知っておく**: 2.5.8 は、文の中のリンクや、ブラウザが決めた大きさのままの部品などを例外にしています。2.1.1 も、手書きの線のように、動きの道筋そのものが要る機能は例外です。例外に当たるか迷う所ほど、実際に使う人に試してもらう価値があります。

**どこから直すか**: まずは主要なタスク（予約）を、キーボードと読み上げで最後まで終えられることを優先します。全部の画面を一度に直すより、タスクが止まる所から直すほうが、使える人が早く増えます。

### [uiux-07-s07] 実践手順: 主要なタスクを、いろいろな方法で試す

根拠: 実務の指針・公式・法令・規格　動画の場面: 11, 12　出典: [W3C Web Accessibility Initiative（WAI） 2024-03-21 更新](https://www.w3.org/WAI/test-evaluate/easy-checks/)、[デジタル庁 2025-10-16 更新](https://www.digital.go.jp/resources/introduction-to-web-accessibility-guidebook)、[W3C Web Accessibility Initiative（WAI） —](https://www.w3.org/WAI/ARIA/apg/patterns/button/)

1. **主要なタスクを決める**: 第 1 章で書いた 1 文（例: 初めての人が、希望の日時で予約したい）と、そのタスクで通る画面を並べる
2. **Tab だけで最後まで**: マウスから手を離し、Tab（次へ）・Shift+Tab（前へ）・Enter・Space だけで進める。届かない所・押せない所・抜け出せない所・進む順番がおかしい所を書き留める
3. **フォーカスを目で追う**: 枠がいつも見えるか、固定の帯やクッキーの帯に全部隠れないかを見る。画面を拡大しても試す
4. **読み上げで聞く**: Windows の NVDA（無料）や PC-Talker、iPhone の VoiceOver、Android の TalkBack などで、ボタン・リンク・画像・入力欄が、名前と役割で分かるかを聞く。「ボタン」とだけ読まれる所は、名前が足りない。デジタル庁のガイドブックは、日本で多くの利用者が使っているのは PC-Talker と NVDA で、Mac の VoiceOver は NVDA などに比べると機能が少ない、としています
5. **指で押す**: スマホで、小さすぎる・近すぎるターゲットを探す。ブラウザの開発者ツールで、大きさ（CSS ピクセル）を測る
6. **点検表に付けて、直す順番を決める**: 図 uiux-07-f04 の 10 項目に、できている・できていない・該当なしを付け、タスクが止まる問題から直す

デジタル庁のガイドブックは、作ったあとで最後に確かめればよい、とならないよう、企画の段階からアクセシビリティを考えに入れるよう勧めています。新しい部品を作るたびに、手順の 2〜4 を一緒に試すのが近道です。

### [uiux-07-s08] 振り返りの問い

根拠: 実務の指針　動画の場面: 13, 14

- 自分のサービスの主要なタスクを、マウスを使わずに最後まで終えられますか？ 途中で、今どこにいるか分からなくなる所はありませんか？

## 5. 理解確認問題

### 問 1. WCAG の 4 つの原則は？

1. 速い・安い・美しい・正しい
2. 知覚可能・操作可能・理解可能・堅牢
3. 色・文字・余白・動き
4. 見る・聞く・話す・書く

<details><summary>答えと解説</summary>

**答え: 2. 知覚可能・操作可能・理解可能・堅牢**

知覚可能（受け取れる形で示す）・操作可能（キーボードなどでも操作できる）・理解可能（内容と操作が分かる）・堅牢（支援技術を含むいろいろな環境で解釈できる）。訳語は WAIC の参考訳。

</details>

### 問 2. div にクリックの処理を付けただけの「ボタン」で、起きやすいことは？

1. 見た目が崩れる
2. Tab キーで届かず、Enter や Space でも押せない
3. 画面の表示が遅くなる
4. 色が変わってしまう

<details><summary>答えと解説</summary>

**答え: 2. Tab キーで届かず、Enter や Space でも押せない**

div は最初からフォーカスを受けず、キーボードで押す動きもない。button 要素なら、どちらも最初から入っている（MDN・WAI-ARIA APG）。div のまま直すなら、role・tabindex・Enter と Space のキーの処理を自分で足すことになる。

</details>

### 問 3. 2024 年 4 月に施行された改正障害者差別解消法で、事業者について正しいのは？

1. ウェブサイトを WCAG 2.2 の AA に合わせることが義務になった
2. 合理的配慮の提供が義務になり、ウェブの改善などの環境の整備は努力義務
3. 合理的配慮の提供は、努力義務のまま
4. 何も変わっていない

<details><summary>答えと解説</summary>

**答え: 2. 合理的配慮の提供が義務になり、ウェブの改善などの環境の整備は努力義務**

第 8 条 2 項の合理的配慮の提供が、努力義務から義務になった。前もって整える環境の整備（第 5 条）は努力義務で、ウェブアクセシビリティの取り組みはこちらに当たる（デジタル庁のガイドブック）。一般的な説明で、個別の判断は専門家に確かめる。

</details>

## 6. 実践課題 [uiux-07-ex] アクセシビリティの 10 項目の点検表と、直す順番

- ねらい: 自分のサービスの主要なタスクを、キーボード・読み上げ・指で試し、10 項目の点検表で問題を見つけて、直す順番を決められる
- 目安の時間: 60〜90 分
- 出すもの: 10 項目の点検表、見つけた問題の一覧（画面・項目・誰がどう困るか）、直す順番とその理由

### 手順

1. 主要なタスクを 1 つ決め（第 1 章の 1 文）、そのタスクで通る画面を並べる
2. マウスを使わず、Tab・Shift+Tab・Enter・Space だけで最後まで進め、届かない所・押せない所・枠が見えない所・隠れる所を書き留める
3. スクリーンリーダー（VoiceOver や NVDA など）で、ボタン・画像・入力欄が、名前と役割で分かるかを聞く
4. スマホで指で押し、小さすぎる・近すぎるターゲットを探して、開発者ツールで大きさを測る
5. 10 項目の点検表（図 uiux-07-f04）に、できている・できていない・該当なしを付ける。自動チェックのツールの結果は、参考として添える
6. できていない項目を「タスクが止まるか」と「直す手間」で並べ、直す順番と、その理由を書く

### 回答例: サンプル予約の「日時を選ぶ」画面（仮の例）

**タスク**: 初めての人が、希望の日時で予約したい（日時 → 連絡先 → 確認）。

**キーボード**: 「予約へ進む」が div で、Tab が届かない（項目 1・6 ができていない）。週を変える矢印も div で、キーボードでは週を変えられない。

**フォーカス**: CSS で outline を消していて、枠が見えない（項目 3）。下に固定した「予約へ進む」の帯に、時間の欄が隠れる（項目 4）。

**読み上げ**: 矢印の画像に alt がなく、何のボタンか分からない（項目 5）。

**指**: 日付の数字が約 20×20 CSS px で、すき間もない（項目 10）。

**直す順番**: ① 「予約へ進む」と矢印を button 要素にする（タスクが止まる・手間が小さい）→ ② 枠を戻し、固定の帯の分の余白を取る → ③ 矢印の alt を「次の週」「前の週」に → ④ 日付のボタンを大きくし、あいだをあける。

### 評価基準

| 観点 | できている | もう一歩 | やり直し |
| --- | --- | --- | --- |
| 試し方 | キーボード・読み上げ・指の 3 つで、主要なタスクを最後まで試している | 1〜2 つの方法だけ、またはタスクの途中まで | 自動チェックのツールだけで済ませている |
| 点検の正確さ | 10 項目すべてに、根拠のある判定が付き、該当なしには理由がある | 判定が付いていない項目や、根拠のない判定がある | 点検表を使っていない |
| 問題の書き方 | 画面・項目・誰がどう困るかが具体的に書かれている | 問題はあるが、誰がどう困るかが抜けている | 「見づらい」など、確かめられない書き方だけ |
| 直す順番 | タスクが止まる問題から並べ、直す手間も考えた理由がある | 順番はあるが、理由がない | 順番を決めていない |

## 7. 要点まとめと参考資料

### 要点

- WCAG 2.2 の 4 つの原則は、知覚可能・操作可能・理解可能・堅牢。達成基準には A・AA・AAA があり、目安は AA
- まず確かめる 5 つ: 代替テキスト（1.1.1）、キーボード（2.1.1）、フォーカスが見える（2.4.7）・隠れない（2.4.11）、ターゲットは 24×24 CSS px 以上（2.5.8、例外あり）
- ボタンは button 要素で作る。div のまま直すと、フォーカス・キーの処理・役割を全部自分で作ることになる
- JIS X 8341-3:2016 は WCAG 2.0 と同じ内容で、改正の作業中。WCAG 2.2 は 2025 年に ISO/IEC 40500:2025 になった
- 改正障害者差別解消法（2024 年 4 月施行）で、事業者の合理的配慮の提供は義務、ウェブの改善などの環境の整備は努力義務（一般的な説明。個別の判断は専門家に）。自動チェックで分かるのは一部で、人が操作して確かめる
